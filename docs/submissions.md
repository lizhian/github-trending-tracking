# 仓库投稿

匿名访客从页头“投稿”提交公开 GitHub 仓库根地址。HTTP 先持久化，后台再获取资料并收录，不需要账号或人工审核。支持 fork、归档仓库；不接受私有仓库及子页面。投稿不会刷新最近上榜时间或既有保护期。

`POST /api/submissions` 接收 JSON `{ "url": "https://github.com/owner/repo" }`，返回 202 和随机投稿 ID。`GET /api/submissions/{id}` 返回本次两类结果和重试时间。结束结果保留 7 天，查询地址应由投稿者保管；页面在本机保存最近一次 ID。

同仓库未完成时合并；已结束后可再投稿。每 IP 滚动一分钟最多 5 次，计数在重启后清空；全站最多 100 个未完成任务，结束或别名记录不计入。429 为 IP 超限，503 为队列已满或维护中，按 Retry-After 稍后重试。

反向代理部署需为 `TRUSTED_PROXY_CIDRS` 设置逗号分隔的可信代理 CIDR，并由入口正确重写或追加 `X-Forwarded-For`。只信任列出的连接来源；其他连接直接按 RemoteAddr 限流。不要将所有公网网段设为可信代理。默认不信任转发头。

## SQLite 升级

投稿表在 schema 4 引入；当前 schema 为 5，为项目增加 Homepage，历史表保持原结构。旧库必须显式迁移，serve 不会自动升级：

1. 用现有版本制作并验证 SQLite 一致备份。
2. 停止应用并等待退出，保留当前镜像 digest 和备份。
3. 使用新版本运行 `trending migrate --db /data/tracking.sqlite`；命令持有同一目录写锁，原子升级，已升级则无操作。不要对生产库运行 init。
4. 使用新镜像启动同一持久目录，执行 verify，并检查页面、投稿结果和下一普通采样时段的真实观测。

新版本能验证和恢复 schema 3、4 的已有备份；恢复后先运行 migrate 再 serve。回退镜像必须支持当前 schema；否则停机保留现有数据库，再恢复升级前备份及旧镜像。恢复备份会撤回之后的投稿和观测。

## 处理语义

GitHub 收录先提交，Linux.do 结果单独完成，复用 README 资格校验和 24 小时不符合缓存。仓库资料和 README 各最多尝试 3 次，失败至少等待 30 分钟；上游限流按共享冷却等待且不计次数。进程重启继续未完成阶段，不等待普通采样时段。

Linux.do 不符合不影响 GitHub 收录；README 三次仍无法确认时显示部分完成，可以再次投稿。Linux.do 已收录时不重复检查 README。清洗维护模式下暂停投稿消费并拒绝新投稿，已有结果查询保持可用。

后台日志仅记录任务阶段和安全诊断，不包含 Token、原始响应或私有仓库资料。结束结果的清理不删除项目或 Star 历史。
